# Domain Modeling Guidelines

This document defines the domain modeling conventions used throughout the project.

Its purpose is to ensure that every module follows the same architectural principles, modeling style, and business language while remaining independent from frameworks, databases, and external providers.

These guidelines apply to every domain module, including:

- Orders
- Payments
- Products
- Users
- Checkout
- Cart
- Future modules

---

# Philosophy

The project follows a pragmatic Domain-Driven Design (DDD Lite) approach.

The objective is to model the business domain without introducing unnecessary complexity.

## Included

- Rich Domain Model
- Aggregate Roots
- Entities
- Value Objects
- Repository Interfaces
- Domain Services (when necessary)
- Business Invariants

## Not Included (for now)

- Event Sourcing
- CQRS
- Sagas
- Specifications
- Complex Domain Events

These concepts may be introduced in the future if the business complexity justifies them.

---

# Rich Domain Model

Business rules belong inside the Domain.

The Domain is responsible for protecting its own consistency.

Business logic must not be implemented inside:

- Presentation
- Infrastructure
- Controllers
- API Routes
- External Providers

The Application layer orchestrates workflows.

The Domain executes business rules.

---

# Aggregate Design

Each Aggregate represents a business consistency boundary.

An Aggregate must:

- Protect its invariants.
- Control its internal state.
- Coordinate its child entities.
- Expose behavior instead of data.

An Aggregate must never:

- Access databases.
- Call HTTP services.
- Use framework APIs.
- Send emails.
- Communicate with payment providers.
- Access external SDKs.

All modifications must go through the Aggregate Root.

---

# Entities

Entities represent business concepts with identity.

Characteristics:

- Have identity.
- May change over time.
- Contain business behavior.
- Protect their own consistency.

Examples:

- Order
- OrderItem
- Payment
- User

Entities should expose meaningful business operations instead of public mutable properties.

---

# Value Objects

Value Objects represent immutable business concepts.

Characteristics:

- Immutable.
- Compared by value.
- Self-validating.
- No identity.
- No lifecycle.

Examples:

- OrderId
- OrderNumber
- Address
- Currency
- CustomerSnapshot
- OrderPricing

A Value Object should be created only when it represents a meaningful business concept.

Do not wrap primitive values without a business reason.

---

# Aggregate Invariants

Aggregates are responsible for enforcing business invariants.

Examples:

- An Order cannot exist without items.
- Order totals must always be consistent.
- Invalid state transitions are rejected.
- Quantities cannot be negative.

Business invariants must never depend on the Presentation or Infrastructure layers.

---

# Domain Services

A Domain Service should only exist when business logic does not naturally belong to a single Entity or Aggregate.

Examples:

- Complex pricing calculations.
- Multi-aggregate business rules.
- Business policies shared by multiple entities.

Domain Services must not contain infrastructure logic.

---

# Repository Interfaces

Repositories belong to the Domain.

Their purpose is to define persistence contracts.

The Domain defines the contract.

Infrastructure provides the implementation.

Repositories should expose business-oriented operations instead of persistence-specific queries whenever possible.

---

# Domain Errors

The Domain should not throw generic errors.

Avoid:

```ts
throw new Error("Invalid Order");
```

Instead, use typed domain errors.

Example:

```text
DomainError
        │
        ▼
OrderDomainError
```

Business failures are identified using error codes.

Example:

```text
OrderErrorCode

EMPTY_ORDER

INVALID_TOTAL

INVALID_STATUS_TRANSITION

ORDER_ALREADY_CONFIRMED
```

Do not create one exception class for every business rule.

Prefer a small hierarchy combined with meaningful error codes.

---

# Enums

Enums represent finite business concepts.

Examples:

- OrderStatus
- PaymentStatus
- RefundStatus

Enums belong to the Domain.

They should never contain business logic.

---

# Object Creation

Entities and Value Objects should expose factory methods.

Preferred:

```ts
const order = Order.create(...);
```

Avoid:

```ts
const order = new Order(...);
```

Factory methods centralize validation and ensure objects are never created in an invalid state.

---

# Identity

The project uses UUID v7 for entity identifiers.

Identifiers are generated by the Application layer or by a dedicated infrastructure service before creating the Aggregate.

The Domain receives valid identifiers and never depends on UUID generation libraries.

Example:

```text
Application

↓

UUID Generator

↓

Order.create(...)
```

The Domain must never depend on UUID libraries.

It only receives valid identifiers.

---

# Module Boundaries

Each module represents an independent business context.

Examples:

- Orders
- Payments
- Products
- Checkout

Modules communicate through:

- Use Cases
- Repository Interfaces
- Service Interfaces
- Identifiers

Modules must never access another module's infrastructure directly.

---

# Business Ownership

Each business concept has a single owner.

Every Aggregate belongs to exactly one module.

That module owns:

- The Aggregate lifecycle.
- Business rules.
- Invariants.
- State transitions.

Other modules may reference the Aggregate through its identifier, but they must never own or modify its internal state.

Examples:

- Order belongs to Orders.
- Payment belongs to Payments.
- Product belongs to Products.

Business ownership must never be duplicated across modules.

---

# Aggregate Communication

Aggregates communicate through identifiers.

Example:

```text
Payment
    │
    ▼
OrderId
```

Avoid direct references between Aggregates.

Correct:

```text
Payment
    │
    ▼
OrderId
```

Incorrect:

```text
Payment
    │
    ▼
Order
```

This keeps Aggregates independent and reduces coupling.

---

# Aggregate Lifecycle

Each Aggregate is responsible for managing its own lifecycle.

External modules may request state changes through business operations, but they must never mutate Aggregate state directly.

Every state transition must enforce the Aggregate invariants.

An Aggregate is the only component allowed to modify its own internal state.

---

# Application Layer Responsibilities

The Application layer coordinates business workflows.

Responsibilities include:

- Executing Use Cases.
- Coordinating multiple Aggregates.
- Using Repository Interfaces.
- Calling external services through abstractions.
- Returning DTOs.

The Application layer should not contain core business rules.

---

# Business Language

The Domain language is defined by the business.

Business terminology must remain stable regardless of implementation details.

Infrastructure adapts external providers to the Domain language.

The Domain must never adapt itself to an external SDK.

Examples of business concepts:

- Order
- Payment
- Payment Status
- Payment Method

Examples of provider concepts:

- Checkout Session
- Payment Intent
- Client Secret
- Preference
- Provider Event

Provider terminology belongs exclusively to the Infrastructure layer.

---

# External Providers

Business modules must never depend directly on external providers.

Always communicate through abstractions.

Correct:

```text
Application

↓

Payment Gateway

↓

Stripe
```

Incorrect:

```text
Application

↓

Stripe SDK
```

This allows payment providers to be replaced without modifying business logic.

---

# Provider Abstractions

The Domain and Application layers communicate with external providers exclusively through abstractions.

Every provider implementation belongs to the Infrastructure layer.

Example:

Application

↓

PaymentGateway

↓

StripePaymentGateway

or

↓

PayPalPaymentGateway

or

↓

MercadoPagoPaymentGateway

Business modules should remain unaware of which provider is currently configured.

---

# Rule of Three

Avoid creating shared abstractions too early.

A reusable domain concept should remain inside its module until multiple independent use cases justify extraction.

Examples:

- Address
- Currency
- Money

When a concept is reused across multiple modules, it may be promoted to a shared domain component.

---

# Naming Conventions

Use consistent names throughout the project.

| Element | Naming |
|----------|--------|
| Aggregate | Order |
| Entity | OrderItem |
| Value Object | Address |
| Repository | OrderRepository |
| Domain Service | OrderPricingService |
| Use Case | CreateOrderUseCase |
| DTO | CreateOrderRequestDTO |
| Mapper | OrderMapper |

Entities use nouns.

Use Cases use verbs.

Repositories represent business contracts.

---

# Decision Process

Architecture decisions should always precede implementation.

When a design question arises:

1. Review the existing documentation.
2. Analyze the business domain.
3. Define the architectural decision.
4. Update the documentation if necessary.
5. Implement the solution.

The project avoids introducing code based on assumptions.

Whenever information is missing, implementation should stop until the required context has been verified.

---

# Technology Independence

Business decisions must always precede technology decisions.

The Domain model is designed first.

Infrastructure adapts technology to the Domain.

Never design the Domain around the capabilities or limitations of a framework, SDK, database, or external provider.

---

# Architectural Goals

The Domain should remain independent from:

- Frameworks
- Databases
- Payment providers
- UI libraries
- Backend technologies
- External SDKs

Business rules should outlive implementation details.

This allows technologies to evolve without affecting the core business model.

The primary goals of the Domain are:

- Maintainability
- Scalability
- Testability
- Flexibility
- Long-term evolution
- Low coupling
- High cohesion
